# AI World Architecture

## Phase 1 Vertical Slice

See the main problem statement for full architectural decisions. This doc captures implementation notes.

## Package Structure

- `packages/shared` — Config (Zod-validated), game-time utilities, action registry, shared types
- `packages/database` — Drizzle schema, migrations, seed (20 chars, 10 locations)
- `packages/game-engine` — Movement validator, wallet atomicity, relationship engine, action validator, directive validator
- `packages/ai` — AgentModelProvider interface, MockProvider (default), AnthropicProvider (gated)
- `apps/simulation-worker` — Tick loop, AI pipeline, event resolution, conversation orchestration
- `apps/web` — Next.js 14, character pages, directive form, SSE feed

## Security Boundary

`packages/game-engine` NEVER imports `packages/ai`.
`packages/ai` NEVER imports `packages/game-engine` or `packages/database`.
Only `apps/simulation-worker` calls both, and only after validation does anything get written.

## Phase 10 — Relationships & Conversations

- `packages/game-engine/src/relationship-engine.ts` is the only code path allowed to write the `relationships` table. Effects are a closed, deltas-only registry (`RELATIONSHIP_EFFECTS`) — the LLM never assigns a trust/affection/etc. value directly, only proposes an action (e.g. `START_CONVERSATION`) that, once validated, triggers a fixed-size engine effect. Every pair is canonicalized (`canonicalizeCharacterPair`) to one row regardless of call order.
- `START_CONVERSATION` / `CONTINUE_CONVERSATION` are validated against per-character visibility (`charactersAtSameLocation`) and open-conversation ownership (`activeConversationIds`), both computed once per tick in `tick-processor.ts` from a batch load (not per-character queries) — see the "Conversation visibility & context" block there.
- A conversation is capped at `MAX_CONVERSATION_MESSAGES` (6) total messages, after which the engine ends it deterministically. Visibility/active-conversation state is a snapshot taken at the start of each tick, so a conversation's target only sees it from their next tick onward — the same single-tick lag MOVE/travel already has.

## Phase 11 — Layered Memory

- `apps/simulation-worker/src/memory-extraction.ts` runs once per COMPLETED game day (hooked to the day-rollover branch in `tick-processor.ts`), never once per tick — §5/§8's "periodic long-term summary, scheduled job, not per-decision cost." A character with zero events that day costs nothing.
- The day's real-time window is computed arithmetically (`gameDayRealTimeWindow` in `packages/shared/src/game-time.ts`) from the world epoch, NOT read off a `game_cycles` row — that row is only created lazily by whichever tick happens to observe a new day number, so a lookup-based window can silently and permanently skip a day that completed without a tick landing in it (this actually happened during development — see git history).
- `AgentDecisionContext.recentMemories` is populated from a per-tick batch load of each character's 5 most recent memories (one query for the whole world, grouped client-side).

## Phase 12 — Economy Depth

- Ships a simple fixed-price NPC market (§6), not player-to-player price discovery: `items.basePriceCents` is what `BUY_ITEM` pays; `SELL_ITEM` pays `basePriceCents * MARKET_SELL_MULTIPLIER` (0.5) — buying and immediately reselling is always a loss, ordinary shop economics.
- `BUY_ITEM`/`SELL_ITEM` are validated to the `market` location by slug (`MARKET_LOCATION_SLUG` in `action-validator.ts`) — hardcoded, matching how the world currently has exactly one market. `GIVE_ITEM`/`TRANSFER_MONEY` instead require the target character to be visible at the same location (reusing the Phase 10 visibility batch-load).
- `packages/game-engine/src/inventory.ts` (`addToInventory`/`removeFromInventory`/`transferItem`) and `wallet.ts`'s new `debitWallet` (the mirror of `creditWallet`, for money leaving the game entirely — an NPC purchase, not a character-to-character transfer) follow the same atomicity rule as `transferMoney`: validate BOTH sides of a transfer before writing EITHER — never mutate one side, then discover the other side can't proceed.
- `GIVE_ITEM`/`TRANSFER_MONEY` are gifts (§5) and trigger a deterministic relationship effect (`ITEM_GIVEN` / `MONEY_GIVEN` in `relationship-engine.ts`) — same closed, deltas-only registry as Phase 10's conversation effects, extended deliberately rather than left for the LLM to decide.

## Phase 13 — Daily Player Report

- `apps/simulation-worker/src/daily-report.ts` runs on the same once-per-completed-game-day hook as Phase 11's memory extraction (same `gameDayRealTimeWindow`-derived window, same "don't backfill a multi-day outage" limitation) — a report is generated from that day's actual `game_events` only (§16: "never fabricated"), via `provider.summarizeEvents` (routed to the strong/dialogue model, §8). Idempotent: a character+day that already has a report is skipped, not duplicated.
- `describeGameEvent` (moved to `packages/shared/src/event-description.ts`) is shared between memory extraction and the daily report — one place turns a raw event into the prose the model sees, so the two features can't drift apart on what a given event type means.
- Surfaced on the character detail page (`apps/web/src/app/characters/[id]/page.tsx`) — last 5 reports, newest game day first.

## Phase 14 — Spectator Broadcast View

- `apps/web/src/app/api/events/stream/route.ts` now resolves `actorCharacterId`/`targetCharacterId`/`locationId` into names, and pre-computes a human sentence (`describeGameEvent`, from `packages/shared`) server-side, before the SSE payload goes out. Found and fixed while building this: `EventFeed`'s `actorName` field had been silently `undefined` since it was written — the route never actually sent it, only the raw id.
- Display formatting is computed **server-side** deliberately, not in the `'use client'` broadcast page — `@ai-world/shared`'s barrel re-exports `load-env.ts` (Node-only `fs`/`dotenv`), so importing the shared package from client code risks pulling that into the browser bundle. The route already runs server-side and already depends on `@ai-world/shared`, so it's the natural place; the client only ever renders pre-formatted strings.
- `/spectate/broadcast` (`apps/web/src/app/spectate/broadcast/page.tsx`) is a full-viewport (`fixed inset-0 z-50`), auto-rotating single-scene view meant for an OBS browser source — connects to the same SSE stream, filters to `importance >= 0.15` (routine noise isn't broadcast-worthy), rotates every 6s through up to 12 recent scenes, and cuts immediately to a fresh sufficiently-important event rather than waiting its turn. It still renders inside the root layout's nav (Next.js App Router composes layouts; there's no per-route opt-out without a multi-root-layout restructure), so the nav bar exists in the DOM underneath it — acceptable for now since the fixed overlay covers it visually, but worth a proper route-group split if this becomes a real OBS dependency.

## Phase 15 — Admin/Debug Console

- `/admin` (gated to `users.role === 'admin'` via `apps/web/src/lib/admin.ts`) answers "why did this character do that" in two clicks: Admin nav link → character. `role` is not part of the NextAuth session object (database session strategy only carries id/name/email/image), so every gate queries `users` by id rather than trusting anything session-cached.
- `/admin/characters/[id]` is the actual answer: `agent_decisions` left-joined to `agent_actions` (intent/goal + valid/rejected/fallback verdict together), a separate "Recent Rejected Actions" pull from `game_events` (there's no FK tying an action to its ACTION_REJECTED event — payload shapes differ, so they're queried and shown separately, not force-joined), per-character AI cost, relationships, and recent memories.
- Simulation Test Mode (Pause/Resume/Run 1 Tick/Run 1 Day/speed multipliers): `packages/database/src/simulation-control.ts` — a single singleton row (`id = 'default'`) the worker's tick loop polls once per iteration and the admin console reads/writes. No queue infrastructure: `claimPendingManualTick` atomically decrements-and-checks in one `UPDATE ... WHERE pendingManualTicks > 0`, which is what keeps "Run 1 Day" (queues N ticks) safe even though today there's only ever one worker process. While paused, the worker polls every 2s instead of the configured tick interval, so admin actions feel responsive rather than waiting out whatever interval was in effect when Pause was pressed.
- No self-service admin promotion exists yet — the first admin is `UPDATE users SET role = 'admin' WHERE email = '...'` by hand. Verified end-to-end against a real NextAuth database session (seeded `users`/`sessions` rows, not a mocked `auth()`) during development: unauthenticated → 307 to `/auth/signin`, signed-in non-admin → 307 to `/`, admin → 200.
- **Test infrastructure fix, found while verifying this live:** `pnpm test` (all packages via one `turbo run test`) was flaking due to cross-*package* Postgres contention — `apps/web`'s and `apps/simulation-worker`'s integration tests, run as separate OS processes by turbo's normal parallelism, hit the same real `DATABASE_URL` concurrently. Per-package `fileParallelism: false` (added for Phase 12's within-package version of this) wasn't enough. Fixed at the root: `"test": "turbo run test --concurrency=1"` in the root `package.json`. Verified: 3/3 clean full-suite runs after the fix, reproduced the failure without it.

## Phase 16 — Alpha Deploy Prep

- `apps/web/Dockerfile` and `apps/simulation-worker/Dockerfile`: multi-stage builds using `turbo prune --docker` to isolate each app's own dependency subgraph, built from the **repo root** (not the app directory — the pnpm workspace needs the full context). `apps/web` additionally uses Next's `output: 'standalone'` (`apps/web/next.config.js`) to keep the runtime image to only the node_modules Next's build tracer determined are actually needed.
- `fly.web.toml` / `fly.worker.toml` (repo root): Fly.io app configs. The worker has no `[http_service]` — it serves no traffic, it's a tick loop — and both pin `GAME_DAY_REAL_SECONDS=86400`/`SIMULATION_TICK_SECONDS=1800` (§12's production values; dev's `.env.example` values are 300/10 and exist to make a "day" watchable in minutes).
- `docs/deployment.md`: the actual runbook — Postgres provisioning, secrets, deploy order, running migrations against production, promoting the first admin, smoke test, rollback. Notes that Redis is provisioned-for-later but not load-bearing today (the tick loop is a plain `setTimeout` loop, not a BullMQ queue, despite those being dependencies).
- **Three real bugs found and fixed by actually running `docker build`/`docker run` rather than treating this as paperwork:**
  1. `packages/*/tsconfig.json` all `extends: "../../tsconfig.json"` — a root-level file `turbo prune`'s pruned output doesn't include (it isn't owned by any single workspace package). Every package's `tsc --build` failed until the Dockerfiles copy it in explicitly.
  2. **`.dockerignore`'s bare `*.tsbuildinfo` pattern only matches at the build-context ROOT, not recursively** (unlike `.gitignore`, Docker's ignore matching needs an explicit `**/` prefix to recurse) — so a locally-generated `packages/database/tsconfig.tsbuildinfo` leaked into the image, and `tsc --build`'s incremental-build check saw a `.tsbuildinfo` newer than the sources and silently emitted nothing, believing a fresh checkout was already compiled. Every pattern in `.dockerignore` now has a `**/` prefix.
  3. `apps/web/src/lib/auth.ts` calls `getDb()` at **module scope** (NextAuth's adapter needs a db instance to construct). Next's "Collecting page data" build step imports every route module — including in worker processes that don't reliably inherit a Docker `ENV`-set `DATABASE_URL` (empirically verified: setting it via `ENV` did not fix the failure; the actual working fix was writing a real `.env` **file**, matching the exact mechanism `apps/web/next.config.js` already uses for local dev, which every worker process re-reads on its own). Fixed by writing that placeholder file in the Docker build stage only, deleted before the runtime image is assembled — never a real secret, never present in the deployed image.
- Also found (and fixed as data hygiene, not a code bug) while running the containerized worker against the shared dev database: an earlier manual cleanup of orphaned test characters had deleted the `characters` rows without ending their open `conversations` — `conversations.participant_ids` is a jsonb array with no FK enforcement, so the dangling reference survived silently until a real seeded character's next `CONTINUE_CONVERSATION` tried to write a `game_events` row with a `target_character_id` that no longer existed. A reminder of exactly why the jsonb double-encoding issue above matters operationally: `jsonb_array_elements_text` on the raw column fails outright (`cannot extract elements from a scalar`) until you know to unwrap it with `(col #>> '{}')::jsonb` first.

## Fixed — jsonb double-encoding (drizzle-orm 0.31.x + postgres.js)

**Status: fixed.** Every `jsonb` column was, since Phase 1, stored double-JSON-encoded — `jsonb_typeof()` returned `'string'` instead of `'object'`/`'array'` on every jsonb column, including seed data. Root cause, confirmed with a direct probe against the `postgres` driver (inserting a raw JS object vs. a pre-`JSON.stringify`'d string into a scratch jsonb column and checking `jsonb_typeof()` on each): `drizzle-orm`'s built-in `PgJsonb.mapToDriverValue` unconditionally `JSON.stringify`s before the value reaches `postgres.js`; `postgres.js`'s own jsonb serializer THEN calls `JSON.stringify` again on whatever it receives, string or not. Drizzle's `mapFromDriverValue` defensively re-parses strings on the way out, which is why every read going through Drizzle (100% of this app's code) was unaffected — the bug was only ever visible to raw SQL.

**Fix:** `packages/database/src/custom-jsonb.ts` replaces drizzle-orm's built-in `jsonb()` with a `customType()`. `toDriver` is pass-through — postgres.js serializes a raw value correctly on its own; nothing left to do on write. `fromDriver` is deliberately NOT a bare pass-through (see the hardening-pass note below): it defensively re-parses a string, so reads self-heal against rows this fix's write path never touched. `schema.ts` imports it aliased as `jsonb`, so none of the 10 column definitions needed to change. Confirmed via `drizzle-kit generate` reporting "No schema changes" (identical `dataType() { return 'jsonb' }`, so no DDL diff) — this is a pure application-layer fix, not a migration.

One packaging gotcha: the import in `schema.ts` deliberately omits the `.js` extension every other relative import in this codebase uses — drizzle-kit's own schema-loading pipeline (separate from this package's own `tsc`) fails to resolve a `.js`-suffixed relative import specifically in `schema.ts`; documented inline at the import site so it doesn't get "fixed" back and silently break `db:generate` again.

**Data migration:** `pnpm db:fix-jsonb-double-encoding` (`packages/database/src/fix-jsonb-double-encoding.ts`) repairs already-corrupted rows — `UPDATE ... SET col = (col #>> '{}')::jsonb WHERE jsonb_typeof(col) = 'string'` per known jsonb column, looped per-column until clean. Every jsonb column in this schema is meant to hold an array or object, never a legitimate scalar string, so that predicate is never a false positive. Idempotent; safe to run again. Run once against the dev database while fixing this: repaired 171,344 row-column values on the first pass (this session's own accumulated tick history).

**Also found while fixing this:** `db:migrate`/`db:seed`/`db:fix-jsonb-double-encoding` were not marked `cache: false` in `turbo.json`, unlike `dev`. A second invocation with no source-file changes and the same `DATABASE_URL` was a turbo cache HIT — it replayed the previous run's logged stdout without actually touching the database. Harmless for `db:seed`'s idempotent inserts, actively dangerous for `db:fix-jsonb-double-encoding` (a "successful" run could report a clean fix while doing nothing) — caught by re-running the fix script immediately after a leftover background `pnpm dev` process (see below) had written more corrupted rows, and getting a cached "already clean" report that raw SQL immediately contradicted. All three now have `cache: false`.

**Also found while fixing this (environment hygiene, not a code bug):** a `pnpm dev` worker process from earlier in the same session had survived multiple `pkill`/`TaskStop` attempts — `tsx watch`'s process tree spawns a child whose own command line doesn't contain "watch", so a `pkill -f "tsx watch ..."` pattern doesn't match it. It kept ticking in the background for over an hour, invisibly writing corrupted jsonb rows the whole time. Found by noticing a raw-SQL spot-check showed a freshly-corrupted row from seconds ago when nothing should have been running; killed by exact PID once located via `ps aux`.

## Hardening Pass — Code Review Fixes

A high-effort automated code review (`/code-review high`) was run over every phase above once Phase 16 landed. Every real finding got a fix and, where practical, a regression test proven to fail without that fix (temporarily reverted, confirmed red, restored, confirmed green — not just "written and left passing"). Findings judged not to be bugs (see the conversations note below) were left alone rather than papered over.

- **`items.base_price_cents` had no default on an already-existing table.** Added in migration 0003 as `NOT NULL` with no `DEFAULT` — safe only because this codebase's own deploy path always runs `db:migrate` before `db:seed` ever inserts an `items` row, but a real risk on any other deploy ordering. Fixed with `.default(0)` and a new migration (`0006_yellow_praxagora.sql`).
- **A duplicate `CONVERSATION_ENDED` event / an extra message past the cap.** `tick-processor.ts`'s per-tick `conversationInfoById` map (built once at the top of the tick from a batch load) wasn't updated when a conversation ended mid-tick via `CONTINUE_CONVERSATION` hitting `MAX_CONVERSATION_MESSAGES` — a second participant continuing the *same* conversation later in the *same* tick still saw it as open in the stale map. Fixed by deleting the entry from `conversationInfoById` the moment the ending event is written, so any later lookup within the same tick sees it as closed. Regression test races two participants continuing one conversation in the same tick and asserts exactly 6 messages, never 7.
- **`addToInventory`'s `SELECT ... FOR UPDATE` locked nothing on a character's very first unit of an item** — there's no row yet to lock, so two concurrent first-purchases could both read "no row," both `INSERT`, and collide (or silently drop one, depending on timing). Fixed with a real DB-level `UNIQUE(character_id, item_id)` constraint (new migration) plus `db.insert(...).onConflictDoUpdate(...)` — the database now enforces the invariant the application code was only hoping to. `transferItem`'s "receiving side gets its first unit of an item" branch gets the identical fix. Regression test races concurrent `addToInventory`/`transferItem` calls against the same character+item.
- **Day-boundary events double-counted between consecutive days' memory extraction/report generation.** `gameDayRealTimeWindow` is a half-open `[start, end)` window — day N's `end` is day N+1's `start` — but both `memory-extraction.ts` and `daily-report.ts` queried with `lte(createdAt, dayEnd)`, so an event landing exactly on the boundary matched both days' queries. Changed to `lt`. Regression tests seed a boundary-timestamp event (given deliberately high importance, since events are queried importance-DESC then capped) and assert it never appears in either day's output.
- **`WORK` wrote a `MONEY_EARNED` game event even when the wallet credit failed.** The action handler inserted the event unconditionally, then attempted `creditWallet` — a `MONEY_EARNED` event with no corresponding balance change whenever `creditWallet` returned `success: false`. Fixed by crediting first and gating the event insert on `credit.success`.
- **`custom-jsonb.ts`'s `fromDriver` was a bare pass-through**, correct only for rows written through this fix's corrected `toDriver` — a row this fix's write path hadn't touched yet (i.e. everything written before `pnpm db:fix-jsonb-double-encoding` runs, or before this fix ships at all on a given deploy) would arrive as a still-double-encoded string and be handed to the application uninterpreted. Added a defensive re-parse: `typeof value === 'string' ? JSON.parse(value) : value`, wrapped in try/catch since a column that legitimately holds a plain string scalar (none exist today, but nothing stops one from being added later) must not throw. Regression test manually writes a double-encoded row with the raw driver and confirms Drizzle's own read path still recovers the original object.
- **`transferMoney`'s lock ordering didn't match its own doc comment.** The comment claimed "locks both rows in a consistent order to avoid deadlocks," but the code locked `fromWallet` then `toWallet` in caller-argument order — consistent *per call*, not consistent *across calls*. Two concurrent transfers going opposite directions between the same two characters (A pays B, B pays A) lock A-then-B in one transaction and B-then-A in the other: a genuine Postgres deadlock (`40P01`), one transaction aborted. Fixed by sorting the lock order by character id, independent of transfer direction — the same pattern `relationship-engine.ts`'s `canonicalizeCharacterPair` already uses for the identical reason. Regression test races five rounds of opposite-direction transfers between the same two characters and empirically reproduced the deadlock against the pre-fix code before the fix was restored.
- **Post-tick scheduling delay used a stale `paused`/`speedMultiplier` snapshot.** `runTick` captured `simulation_control` once at the top of the function to decide whether to run at all, then reused that *same* value at the bottom to compute the delay before the next tick — an admin clicking Pause (or changing the speed multiplier) while a tick was mid-flight (an AI round-trip can take a while) wouldn't be reflected until a whole extra tick interval later (up to 30 minutes in production). Fixed by re-fetching `simulation_control` at the point the delay is actually computed.
- **Per-character AI extraction loops (`memory-extraction.ts`, `daily-report.ts`) ran sequentially.** Each character's pass is dominated by one AI round-trip, not CPU, and touches no other character's rows — nothing about the loop needed to be sequential, and running it that way stalls the day-boundary tick for `roster_size * round_trip_latency`. Rewritten around `Promise.all` over a per-character helper that still isolates errors exactly the way the old `try`/`catch`-per-iteration loop did (one character's failure can't affect another's, and `charactersProcessed`/`memoriesWritten`/`reportsWritten` preserve the exact "partial progress still counts" semantics the sequential version had).

  Parallelizing surfaced a real hazard along the way, not just a mechanical loop rewrite: `AnthropicProvider` tracked per-call token/cost usage as **one shared `lastUsage` field**, read afterward via a separate `provider.getLastCallUsage()` call — safe only because every existing call site awaited one provider call at a time. Once N characters' `extractMemory`/`summarizeEvents` calls are in flight concurrently against the same provider instance, that shared-field read races the *other* characters' concurrent calls — the JS event loop offers no ordering guarantee across two independent in-flight network requests each with several of their own internal `await` hops, so which character's usage a given `getLastCallUsage()` call actually observes depends on network timing, not which character made the call. Left as a naive `Promise.all` over the old API, this would have silently mis-attributed AI cost between characters — a regression a passing test suite wouldn't catch, since `MockProvider` has no meaningful latency to expose the race.

  Fixed at the interface level, not by limiting concurrency: `SummaryResult`/`MemoryResult` (`packages/shared/src/types.ts`) now carry usage inline (`usage?: AiCallUsage`) as part of the method's own return value, so each call's usage travels with that call's own result instead of through shared instance state. `AnthropicProvider.extractJson` returns `{ parsed, usage }` from one computation instead of two, and `summarizeEvents`/`extractMemory` attach it to their result; `decideAction`/`generateDialogue`/`moderateDirective` are untouched (still sequential per character in `tick-processor.ts` today) and keep using the `lastUsage` side effect. `provider.ts`'s `getLastCallUsage` doc comment now states explicitly which calling pattern it's safe for. Regression tests in `memory-extraction.test.ts`/`daily-report.test.ts` race two characters through a fake provider that resolves the *first-called* character *last*, with a distinct, identifiable cost per character, and assert neither ends up with the other's cost — proven to fail (usage reads back as `0`, since the fake provider deliberately doesn't implement `getLastCallUsage`) when the fix is reverted to the old side-channel read.

**Investigated, not changed:** two characters simultaneously issuing `START_CONVERSATION` at each other in the same tick can each independently create a `conversations` row and independently apply the `CONVERSATION_STARTED` relationship effect — a duplicate conversation row and a doubled relationship delta. This is a pre-existing, already-documented limitation from the original Phase 10 work (per-tick visibility/conversation state is a snapshot, not live-checked mid-tick — the same batch-load design documented throughout this file), not a new discovery from this pass. Left as-is: fixing it properly needs either a DB-level uniqueness constraint on an unordered character pair (harder than `inventory`'s fix — conversations aren't keyed by a fixed pair the way inventory is by character+item) or a same-tick liveness check that would undercut the batch-load design's whole performance rationale, for a cosmetic-only failure mode (an extra relationship point, not a state-corrupting one). Worth a real fix if conversations ever need a stronger uniqueness guarantee for other reasons; not on its own.

## Live Validation Pass — Actually Running the Alpha, Not Just Testing It

After the hardening pass above merged, the honest next step wasn't more features — it was checking whether the fully-hardened alpha actually meets §16's own stated success bar ("20 characters running several simulated days produce friendships, rivalries, competition, alliances, deception, reputation shifts — unscripted"). A passing test suite proves each piece works in isolation; it doesn't prove the assembled system behaves sensibly over real, sustained operation. So: both apps were actually launched (`pnpm dev` in `apps/simulation-worker` and `apps/web`) against the dev database's accumulated 228-day / 62k-event history, driven live (homepage, character pages, `/spectate/broadcast`, the SSE event stream, all hit directly), and the data was inspected for real, not assumed.

**What held up:** wallet accounting reconciled exactly — total wallet balance across all 20 characters equalled starting balances minus everything ever debited to the outside world (NPC purchases) plus everything ever credited from it (wages), with zero drift after 228 days and tens of thousands of ticks; zero negative inventory rows; the SSE feed's actor/target/location name resolution (the Phase 14 fix) confirmed working live, not just in the route's own logic.

**What didn't, and got fixed — `AgentDecisionContext` never told the model which MOVE destinations were reachable.** Location `connections` are one-directional (confirmed from live data: `bank`'s connections include `market`, but `market`'s connections do not include `bank` back) and `isLocationConnected` only ever allows a direct one-hop move, but nothing in the decision context exposed that adjacency list — `MockProvider`'s MOVE logic hardcoded "always target town-square" (or `tavern` if already there) with no awareness of whether that was reachable, and the real prompt sent to `AnthropicProvider` had no equivalent field either. The live data made the cost of this concrete: 5,580+ `ACTION_REJECTED` events accumulated over 228 days from just two characters standing at `bank`/`mine` (neither directly adjacent to `town-square`), permanently proposing the same invalid move every single tick, forever — not a crash, but a silent, indefinite waste of every decision cycle for any character who ends up somewhere not one hop from the hub. Under `AnthropicProvider` this is real spent money on every one of those calls, not just a mock artifact — directly contradicts §5/§8's own cost-discipline principle.

Fixed by adding `connectedLocationSlugs: string[]` to `AgentDecisionContext`, populated in `tick-processor.ts` straight from the already-batch-loaded `locationMap` (no new query). `AnthropicProvider`'s user message now includes it as `move_destinations_available`, with an explicit system-prompt rule that a MOVE's `target_id` must come from that list. `MockProvider`'s MOVE logic (`pickMoveDestination`) now picks a real reachable destination — `town-square` when it's reachable, otherwise the first other connection, falling back to `IDLE` only when truly nothing is reachable (an isolated/test-fixture location) — deterministic, same as before, just no longer blind.

**Verified live, not just via the new regression tests** (`mock-provider.test.ts`'s three new cases, each proven to fail against the pre-fix hardcoded logic): with both dev processes still running, the character that had been stuck at `bank` for 228 days moved to `city-hall` — a real, valid connection — within one tick of the fix landing, then went on to start a conversation. Zero `ACTION_REJECTED` events of any kind occurred anywhere in the world in the time since. Timestamp discipline mattered here: the dev database's `created_at` columns are `timestamp without time zone` (UTC clock values with no zone attached), and the local psql session's zone is `America/Los_Angeles` — a raw `now() - interval` comparison against that column silently casts `now()` down to local wall-clock digits, comparing against UTC clock digits stored in the column, which is wrong by the zone offset and was initially misread as "the fix isn't working" before adding an explicit `at time zone 'utc'` cast to the ad hoc query. The application code itself was never at risk of this — it always compares real JS `Date` objects through drizzle, never raw SQL `now()` — but it's a sharp edge worth remembering for the next person debugging this database directly with `psql`.

Also confirmed clean during this same pass, as basic invariant spot-checks against the live 228-day dataset: no relationship dimension ever outside `[-100, 100]`, no `character_state` row with `health`/`fatigue` outside `[0, 100]`, and no conversation with more than the `MAX_CONVERSATION_MESSAGES` (6) cap — all held with zero violations across the entire history, not just in the unit tests that assert the clamping/cap logic in isolation.

## CI — GitHub Actions (`.github/workflows/ci.yml`)

Every one of this repo's merges up to this point relied entirely on a human (or an agent) remembering to run `pnpm turbo run typecheck lint test` locally before pushing — nothing on GitHub's side ever verified that. Added a `verify` workflow (typecheck, lint, test) that runs on every push to `main` and every PR, against a real `postgres:16` service container — not skipped, the way every integration test's `describe.skipIf(!DB_URL)` silently no-ops locally without a `DATABASE_URL`. `AUTH_SECRET` is a fixed CI-only placeholder (config.ts only requires it be non-empty; nothing in the suite exercises real auth against it); `AI_USE_LIVE` stays at its default `false` so no `ANTHROPIC_API_KEY` is needed — every test in this suite runs against `MockProvider`, same as local dev without live AI explicitly opted into.

Verified by actually reproducing the workflow's exact command sequence locally against a **fresh** database (`db:migrate` → `db:seed` → typecheck/lint/test, no pre-existing dev history) rather than trusting the YAML would work untested — and it caught a real gap on the first attempt: `tick-integration.test.ts`'s economy-actions case looks up the seeded `market` location by slug rather than creating its own fixture, so it fails against a migrated-but-unseeded database with a clear error pointing at the fix (`pnpm db:seed`). Every other integration test in the suite seeds its own fixtures in `beforeAll` and doesn't need this — added the seed step anyway since the one test that does need it is real coverage, not incidental.

**A second, more consequential gap only the real GitHub-hosted runner caught, not the local rehearsal above:** the actual first CI run failed at `db:migrate` with `Cannot find module '.../packages/database/node_modules/@ai-world/shared/dist/index.js'`. `turbo.json`'s `db:migrate`/`db:seed`/`db:fix-jsonb-double-encoding` tasks never declared `dependsOn: ["^build"]` — unlike `typecheck`/`test`, which do — so turbo never knew `@ai-world/database`'s scripts need `@ai-world/shared` built first. This is a real, pre-existing bug in the repo's own task graph, not a workflow-authoring mistake: it only ever "worked" locally by accident, because this machine's `dist/` directories were always already populated by whichever `typecheck`/`build`/`test` command had most recently run in this same long session — a genuinely fresh clone was never exercised until the GitHub-hosted runner did it. My own local "fresh database" rehearsal for the gap above didn't catch this either, because resetting the database isn't the same as resetting `dist/`. Re-verified properly this time: `rm -rf`'d every package's `dist/`, `.tsbuildinfo`, and `.turbo` cache, then re-ran the full `migrate → seed → typecheck → lint → test` sequence from that genuinely clean state locally before trusting it, in addition to letting the real workflow re-run on the PR. Fixed by adding the missing `dependsOn: ["^build"]` to all three `db:*` write tasks (`db:generate` correctly stays without it — `drizzle-kit`'s schema loader transpiles `schema.ts` directly and never imports `@ai-world/shared`, so it has no such dependency).

This workflow only reports status — it doesn't block a merge by itself. Pairing it with a branch protection rule on `main` requiring it to pass is a repo-settings change outside what a commit can express, and was attempted directly after this PR merged: GitHub's branch-protection API returns `403` on this repo today (`Upgrade to GitHub Pro or make this repository public to enable this feature`) — this repo is private, on the free plan, and branch protection on a private repo needs one or the other. Deliberately left unprotected rather than making the repo public to work around it. Revisit if the repo ever goes public or the plan changes.

## World Map — `/spectate`'s top-down view (`WorldMap.tsx`)

The alpha's `/spectate` page shipped as a text event feed plus a character-status list — accurate, but not what "watch a world" reads as to someone expecting an MMORPG-style view of avatars standing in a place. The build plan is explicit that this is deliberate for the alpha (§2: "graph of locations, not a map"; §append: "optimize for testing [the directive-steering hypothesis], not scale or graphics"), so there was never any authoritative x/y anywhere in the schema to render from. `WorldMap.tsx` adds a presentation-only 2D layer on top of the existing simulation without touching it: `lib/world-layout.ts` hand-places one `{x, y}` per seeded location slug (`LOCATION_LAYOUT`), roughly mirroring the seed's connections graph so edges between connected nodes don't cross more than necessary. Any location slug without an entry there — in practice, leftover `*-test-*-slug` fixture rows other integration test suites insert and never clean up in this long-running dev database — is dropped rather than guessed at, both by `/api/world/snapshot` (server-side, regression-tested in `snapshot/__tests__/route.test.ts`) and defensively again in `WorldMap` itself.

Two independent data sources feed the view, deliberately not merged into one: `/api/world/snapshot` (new), polled every 5s, is the authoritative who's-where-and-doing-what — self-healing, since a missed poll just means a few stale seconds corrected by the next one. The existing `/api/events/stream` SSE feed is layered on top purely for transient effects — speech bubbles on `CONVERSATION_STARTED`/`CONVERSATION_MESSAGE`, a dashed travel-pulse line on `CHARACTER_MOVED`, floating +/-¢ toasts on money/item events — plus an optimistic per-character location override applied immediately on `CHARACTER_MOVED` so movement reads as live rather than waiting out the next poll; the next snapshot always wins over the override, so a dropped SSE event costs one animation, never a wrong position.

**A real legibility bug, caught only by actually looking at a screenshot of a live, populated world, not by typecheck/lint/tests:** the first version placed each character at a location via an independent per-character hash offset (stable angle + radius derived from hashing their id alone). At this project's real density — 20 characters across 10 locations, several of them political hubs everyone gravitates toward — City Hall and the Tavern regularly hold 4-5 characters at once, and independent per-character hashing has no way to know about siblings, so their name labels collided into unreadable run-together text (confirmed via a headless-Chrome screenshot of `/spectate`, not just eyeballing the JSX). Fixed by computing offsets per-location-group instead: `characterOffsetWithinLocation(indexWithinLocation, countAtLocation)` evenly spaces however many characters are actually standing at that location around a ring, with the ring's radius growing with the crowd size, a special-cased left/right split for the (most common) two-character case so conversation pairs' labels land beside each avatar rather than under it, and name-label anchoring that points outward (side-anchored `start`/`end` for a horizontal offset, centered-below only for near-vertical ones) — the same technique map-pin labels use to avoid colliding with their neighbors. Grouping is keyed off the *effective* (override-applied) location so a character mid-transition doesn't jump ring slots the instant their optimistic override lands.

Verified against the live dev database (228+ days of real simulated history, not a fixture): the snapshot route correctly resolves all 10 seeded locations and skips accumulated test-fixture rows; a headless-Chrome screenshot of `/spectate` under real concurrent load showed five simultaneous conversation speech bubbles, a traveling character's dashed pulse line, and correctly color-ringed statuses (idle/working/traveling) with no label collisions after the per-location-group fix.

## `AgentDecisionContext.inventory` — the same class of gap the MOVE fix closed, found in `SELL_ITEM`/`GIVE_ITEM`

`SELL_ITEM` and `GIVE_ITEM` were both in `availableActions` and the action registry from Phase 12 onward, but nothing in `AgentDecisionContext` ever told the model what a character actually owns. `action-validator.ts`'s checks for both only confirm the referenced item id exists in the world's *global* catalog (`world.itemIds`), not that this character holds any of it — the real ownership check happens at execution time in `game-engine/inventory.ts`'s `removeFromInventory`/`transferItem`, which fail closed (an `ACTION_REJECTED`, never a negative balance). So the actions were safe, just permanently blind: `MockProvider` never had a branch that proposed either one at all (dead code, unconditionally, regardless of what the model could see), and `AnthropicProvider`'s prompt had no `inventory` field for a real model to ground a proposal in — any `SELL_ITEM`/`GIVE_ITEM` it emitted could only be a guess at an item id it happened to remember from `available_market_items` (the same global catalog BUY_ITEM draws from), with no way to know if this character currently held any.

Fixed the same way as the MOVE gap: added `inventory: InventoryItemSummary[]` (`{itemId, name, quantity}`, quantity > 0 only) to `AgentDecisionContext`, batch-loaded once per tick in `tick-processor.ts` (one query joined against the already-loaded `itemById` map, not per-character), exposed to `AnthropicProvider`'s prompt as `inventory` with a new RULES line that SELL_ITEM/GIVE_ITEM must reference an id actually present there. `MockProvider` gained real branches for both — SELL_ITEM when standing at the market already holding stock (checked before BUY_ITEM, so surplus gets cashed in before a fresh purchase), GIVE_ITEM when holding stock elsewhere with someone visible to give it to — always sourced from `ctx.inventory`, never fabricated. Three new regression tests in `mock-provider.test.ts` cover SELL_ITEM, GIVE_ITEM, and (previously untested at all) the plain BUY_ITEM case, to guard the branch ordering now that SELL_ITEM sits ahead of it.

**Found late in the same session as a live-DB test-flakiness side effect, not by design:** re-running the full suite against this project's long-running dev database (by this point 1,000+ real ticks, 2,300+ real memory rows) surfaced a pre-existing, unrelated flake in `tick-integration.test.ts`'s "recentMemories reaches the decision context" test — proven via a `git stash` re-run to fail identically with or without this fix, so not a regression here. Root cause: `recentMemoriesByCharacterId` (tick-processor.ts) queries the globally most-recent 1000 memory rows and buckets them per character client-side; against a database this active, a freshly-inserted single test memory can be crowded out of that global top-1000 entirely by real simulation volume before the test ever reads it. Real CI (a fresh `postgres:16` container per run) never hits this — noted here rather than fixed, since the actual fix (scoping the query per-character in SQL, e.g. a `DISTINCT ON`/window function, instead of a global-cap-then-bucket) is a real but separate improvement, not part of this one.
